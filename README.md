# לוח בקרה ניהולי — נכסי אירוח באירופה

לוח בקרה (Dashboard) בעברית, RTL מלא, לחברת נדל"ן ישראלית המנהלת מלונות,
פנסיונים ודירות נופש באירופה. המערכת מציגה רווח והפסד, הכנסות, הוצאות,
תפוסה, הזמנות, תחזוקה, חריגות, השוואת תקופות ועמידה ביעדים חודשיים —
מתוך **קובץ Excel שאתה מעלה לאתר**.

**מודל העבודה:** בכל פעם שאתה מעלה את קובץ ה-Excel, הנתונים מתעדכנים
לפי הקובץ. אין שרת, אין חיבור חי, אין התקנות מצד Microsoft — פשוט מעלים
קובץ והכל מתחשב מחדש. הקובץ שהועלה נשמר בדפדפן (localStorage), כך שאחרי
רענון הדף הנתונים נשארים עד שמעלים קובץ חדש או מנקים אותם.

> **שלב MVP — לצפייה בלבד.** אין עריכה ואין שינוי של הקובץ. המערכת
> מתייחסת לקובץ ה-Excel כמקור קריאה-בלבד (read-only), והקובץ לעולם לא
> עוזב את הדפדפן — אין העלאה לשרת חיצוני.

---

## 1. מה נבנה

אפליקציית **React 18 + TypeScript + Vite + Tailwind CSS**, עם תרשימים
ב-**Recharts** וקריאת קבצי Excel באמצעות **SheetJS (`xlsx`)**.
**שנים-עשר מסכים**, תפריט צד בעברית (Sidebar בדסקטופ, ניווט אופקי
במסכים קטנים), פס פילטרים גלובלי, וכפתור **"העלאת קובץ Excel"**.
האפליקציה היא frontend-only לחלוטין — אין שרת, API, מסד נתונים או
ניתוב (React Router); הניווט בין המסכים מנוהל דרך `PageKey`/`NAV_ITEMS`
ו-state מקומי ב-`App.tsx`.

המסכים (לפי סדר התפריט):

1. **דאשבורד ראשי** — כרטיסי KPI, הכנסות מול הוצאות, רווח/הפסד לפי נכס,
   פילוח לפי פלטפורמה, פילוח הוצאות, נכס מוביל/חלש, וטבלת סיכום כל הנכסים.
2. **נכסים** — כרטיס לכל נכס, טבלת חדרים, וטבלת עמלות לפי פלטפורמה.
3. **רווח והפסד (P&L)** — דוח מפורט (שורות = סעיפים, עמודות = נכסים) + שינוי חודשי.
4. **השוואת תקופות** — השוואת ביצועים בין תקופה נוכחית לקודמת (שבוע/חודש/
   רבעון/שנה מול תקופה מקבילה, 7/30 הימים האחרונים, מתחילת החודש/השנה,
   או טווח תאריכים מותאם אישית). כוללת KPI-ים פיננסיים ותפעוליים זה-לצד-זה,
   גרפים חופפים לפי יום, פירוט לפי נכס, ותובנות טקסט שנגזרות אוטומטית
   מהנתונים (לא AI). ראו סעיף 7 להרחבה.
5. **יעדים חודשיים** — השוואת הכנסות/הוצאות/רווח/שולי-רווח בפועל מול יעדים
   חודשיים קבועים, לכל נכס או לכלל הנכסים שיש להם יעד מוגדר. ראו סעיף 8
   להרחבה.
6. **הכנסות** — לפי נכס, חודש, פלטפורמה, וסוג הכנסה (הזמנות / הכנסות נוספות).
7. **הוצאות** — לפי קטגוריה, סטטוס תשלום, אמצעי תשלום; סכום מלא / ששולם / נותר.
8. **הוצאות חד פעמיות** — מגיליון נפרד "One-time expenses" (אותו מבנה כמו
   Expenses), עם KPI-ים, פילוח לפי קטגוריה וטבלה משלו. **מאגר נתונים נפרד
   לגמרי** — לא נכלל בחישובי רווח והפסד / "סך הוצאות" הרגילים. ראו סעיף 9.
9. **תפוסה** — לפי נכס, חודש וחדר; לילות תפוסים מול לילות זמינים.
10. **הזמנות** — כל ההזמנות מגיליון occupation, עם סינון לפי סטטוס.
11. **תחזוקה** — דיווחי תקלות, עלויות וסטטוסי טיפול.
12. **חריגות בנתונים** — התראות אוטומטיות (לא AI) על הפסדים, הוצאות/הכנסות
    חריגות, נתונים חסרים ועוד. המודול רק **מזהה ומציג** בעיות — לעולם לא
    מתקן או משנה נתונים (`src/lib/anomalies.ts`).

## 2. איך להריץ

```bash
npm install
npm run dev
```

הדפדפן ייפתח אוטומטית ב-`http://localhost:5173`. לבנייה לפרודקשן:
`npm run build` (מריץ `tsc` ואז `vite build`) ואז `npm run preview`.

### איך מעלים את הקובץ ומעדכנים נתונים

יש שתי דרכים זהות להעלאה:

1. כפתור **"העלאת קובץ Excel"** הכחול בראש המסך (למעלה משמאל).
2. אזור הגרירה (Drag &amp; Drop) שמופיע במצב דמו — גוררים אליו את הקובץ.

ברגע שמעלים קובץ: כל הנתונים, המדדים, הגרפים והטבלאות מתחשבים מחדש,
החיווי הופך לירוק **"מעודכן מקובץ Excel"**, וזמן העדכון מתעדכן.
בכל העלאה חוזרת — הנתונים מתחלפים לחלוטין לפי הקובץ החדש (אין מיזוג
בין קבצים).

> הקובץ שהועלה נשמר ב-`localStorage` של הדפדפן (מפתח
> `properties_dashboard_dataset_v1`), כך שרענון הדף לא מאבד את הנתונים.
> כפתור **"נקה / דמו"** מנקה אותם וחוזר לתצוגת הדמו.

## 5. איך מתבצעים החישובים

הכול מחושב **ישירות מגיליונות המקור** (occupation, Extras, Expenses, Maintence,
Rooms, Properties) — לא מהגיליונות המוכנים (Pivot / P&L) שב-Excel. שכבת
החישוב המרכזית היא `src/lib/calculations.ts`.

### שכבת הרווחיות הרשמית — מקור אמת יחיד

הפונקציות הרשמיות שכל מסך/KPI/השוואת-תקופות/יעדים **חייבים** להשתמש
בהן (ולא לחשב הכנסה/הוצאה/רווח בעצמם):

| פונקציה | חישוב |
|---|---|
| `calcRevenue` | הכנסות ברוטו מהזמנות (`TotalPrice`) + הכנסות נוספות (Extras `Amount`) |
| `calcExpenses` | `FullAmount` של כל שורות Expenses (ללא קשר לסטטוס תשלום) + תחזוקה (Maintence `Amount`) + עמלת פלטפורמה (`commission`) |
| `calcProfit` | `calcRevenue` − `calcExpenses` |
| `calcProfitMargin` | `calcProfit` / `calcRevenue` (0% כשההכנסה 0 — לעולם לא `Infinity`/`NaN`) |

דוח ה-P&L (`buildPnL`) מציג הכנסות ברוטו לפי פלטפורמה (Booking / Airbnb /
אורח מזדמן) ועמלות כשורת הוצאה נפרדת — ומחושב באמצעות אותה שכבה
(`calcProfit`/`calcProfitMargin`), כך שהרווח/שולי-הרווח זהים אלגברית לכל
מקום אחר באפליקציה עבור אותו נכס ואותם פילטרים.

> **קיימת גם שכבה נטו נפרדת** (`totalRevenue`/`totalExpenses`/`netProfit`/
> `profitMargin`, המבוססת על `TotalNetPrice` — הכנסה לאחר ניכוי עמלה).
> היא משמשת כמידע משלים ("הכנסות נטו") במקומות ספציפיים בלבד, **ואינה**
> משמשת עוד לחישוב שולי הרווח הרשמיים — כי המכנה שלה שונה מזה שה-P&L
> (המקור הסמכותי) משתמש בו. אין להשתמש בה עבור KPI-ים רשמיים חדשים.

### הוצאות חד-פעמיות (One-time expenses)

גיליון נפרד, באותו מבנה בדיוק כמו Expenses. מוצג במסך משלו בלבד
(`OneTimeExpenses.tsx`), ו**אינו** נכלל בחישוב `calcExpenses`/`calcProfit`/
`calcProfitMargin` / דוח ה-P&L הרגילים — בכוונה, כדי לשמור על שני המאגרים
נפרדים. ההפרדה נאכפת בכל שכבות הקוד: טיפוסים (`OneTimeExpense` נפרד מ-
`Expense` ברמת השדה, גם אם מבנהו זהה), נורמליזציה (`normalizeOneTimeExpenses`
קורא מגיליון "One-time expenses" בלבד), פילטרים (`data.oneTimeExpenses`
מסונן בנפרד לגמרי ב-`filterDataSet`/`filterDataSetByRange`), וכל פונקציות
החישוב (`oneTimeExpensesPaid/Full/Left`, `oneTimeExpensesByCategory`) — לא
רק בתצוגה.

### שיוך רשומה לחודש/תאריך — מקור אמת יחיד

כל שיוך של רשומה לחודש (לצורך פילטור, קיבוץ וסיכומים) וכל שיוך לתאריך
מדויק (לצורך "השוואת תקופות") עוברים דרך אותו זוג פונקציות ייעודיות
לכל סוג גיליון, ב-`src/lib/calculations.ts` — אין שכפול של לוגיקת התאריך
במקום אחר (כולל פס הפילטרים, טבלאות, גרפים, השוואת תקופות ויעדים):

| גיליון | פונקציית תאריך גולמי | פונקציית מפתח-חודש | שדה קובע |
|---|---|---|---|
| occupation (הזמנות) | `occDate` | `occMonth` | `Check-in Date` בלבד (גם אם ה-`Check-out` בחודש הבא) |
| Extras (הכנסות נוספות) | `extraDate` | `extraMonth` | עמודת `Month`, עם נפילה חזרה (fallback) ל-`Date` אם `Month` חסר |
| Expenses (הוצאות שוטפות) | `expenseDate` | `expenseMonth` | `BillingDate`, עם נפילה חזרה ל-`Month` ואז ל-`InvoiceDate` |
| One-time expenses | `expenseDate` | `oneTimeExpenseMonth` | אותה לוגיקה בדיוק כמו Expenses (אותה פונקציית תאריך גולמי) |
| Maintence (תחזוקה) | `maintDate` | `maintMonth` | `Date` בלבד |

`filterDataSetByRange` (המשמשת את "השוואת תקופות") משתמשת באותן פונקציות
תאריך גולמי בדיוק (`occDate`/`extraDate`/`expenseDate`/`maintDate`) — רק
בודקת השתייכות לטווח תאריכים מדויק במקום התאמת מפתח-חודש — כך שאין אף
פעם שתי לוגיקות שיוך-תאריך שונות לאותו סוג רשומה.

> **טיפול בשגיאות הכתיב שבקובץ** (ב-`normalize.ts`): המערכת מזהה גם
> `ProperyName`, `Commision %`, `Maintence`, `InvocieDate`, ו-`occupation`
> באותיות קטנות — בלי לקרוס, ועם רשימת שמות-חלופיים (aliases) לכל שדה.

## 6. פילטרים גלובליים (`FilterContext`)

מוגדרים ב-`src/context/FilterContext.tsx` ומוצגים דרך `FilterBar`:

- **נכס** (`propertyId`)
- **מדינה** (`country`)
- **שנה** (`year`)
- **חודש** (`month`)
- **פלטפורמה** (`platform`)

רוב המסכים (דאשבורד, נכסים, P&L, הכנסות, הוצאות, הוצאות חד-פעמיות, תפוסה,
הזמנות, תחזוקה, חריגות) משתמשים ב-`useFilters()` ישירות ומסננים דרך
`filterDataSet`.

שני מסכים משתמשים בפילטרים הגלובליים באופן חלקי בלבד, כי החלת כל חמשת
הפילטרים הייתה משנה את המשמעות העסקית של המסך:

- **השוואת תקופות** — משתמש בפילטר הגלובלי של **נכס** ו**מדינה**, אך
  יש לו בקרות תאריך משלו (מצב השוואה, רבעון, טווח מותאם אישית) **במקום**
  פילטרי **שנה/חודש** הגלובליים — כי המסך משווה שני טווחי-תאריכים מחושבים
  (לא חודש קלנדרי בודד). פילטר **פלטפורמה** אינו מוצג במסך זה.
- **יעדים חודשיים** — משתמש בפילטרי **מדינה** ו**פלטפורמה** הגלובליים
  (`baseFilters`), אך לבחירת **נכס** ו**שנה/חודש** יש לו בורר ייעודי
  משלו במסך, כי היעדים מוגדרים דרך `src/data/targets.ts` ולא ניתן להציג
  יעד עבור צירוף שרירותי של פילטרים גלובליים.

## 7. השוואת תקופות (`src/lib/periods.ts`)

לוגיקת חישוב טווחי תאריכים (נוכחי + קודם) לכל מצבי ההשוואה מרוכזת
כולה ב-`src/lib/periods.ts`. עצם הסינון של הנתונים לפי הטווח שמחושב
כאן נעשה דרך `filterDataSetByRange`/`dailySeriesForRange` ב-
`src/lib/calculations.ts` — כך שאין כפילות של כללי שיוך-תאריך, רק
כפילות של "אילו שני טווחי ימים משווים".

**מצבי השוואה נתמכים** (`ComparisonMode`):

- שבוע מול שבוע (`wow`)
- חודש מול חודש (`mom`)
- רבעון מול רבעון (`qoq`)
- שנה מול שנה (`yoy`)
- 7 הימים האחרונים (`last7`)
- 30 הימים האחרונים (`last30`)
- מתחילת החודש — Month to Date (`mtd`)
- מתחילת השנה — Year to Date (`ytd`)
- טווח תאריכים מותאם אישית (`custom`)

**הגדרת שבוע:** ראשון עד שבת (`sundayOf` — יום ה-`getUTCDay() === 0`
הוא תחילת השבוע).

**כלל-העל — לא משווים תקופה חלקית מול תקופה מלאה:** אם התקופה הנוכחית
עדיין באמצע (כוללת את "היום", למשל חודש נוכחי שטרם הסתיים), שתי התקופות
(נוכחית וקודמת) נחתכות לאותו מספר ימים בדיוק, החל מתחילתן (`pairFromNominal`
+ `clampToToday`). כנ"ל ב-`monthToDate`/`yearToDate` כשהחודש/השנה הקודמים
קצרים יותר (למשל 29 בפברואר בשנה מעוברת). הלוגיקה הזו — "טווח שווה-אורך"
— מרוכזת ב-`previousEqualLengthRange`/`rangeOfLength` ואינה משוכפלת
בקומפוננטות.

**קוטביות KPI (`KPI_POLARITY`):** לא כל עלייה היא חיובית. לדוגמה: הכנסה
גבוהה יותר = טוב, רווח גבוה יותר = טוב, **הוצאות גבוהות יותר = רע**
(`down-good`). כל מקום שמציג חץ/צבע של שינוי (ירוק/אדום) חייב להשתמש
ב-`KPI_POLARITY` + `isGoodChange`, ולא להניח שעלייה=ירוק תמיד.

## 8. יעדים חודשיים (`src/data/targets.ts` + `src/lib/targets.ts`)

**תצורת היעדים** (`src/data/targets.ts`, `MONTHLY_TARGETS`) היא נתון קבוע
בלבד — ללא לוגיקה. כל יעד הוא **חודשי** (חוזר על עצמו בכל אחד מ-12 חודשי
השנה, לא יעד שנתי), ומוגדר לפי `PropertyID` (אותם מזהים כמו בגיליון
Properties). נכס/שנה שלא מופיעים בקובץ **פשוט אין להם יעד מוגדר** —
אסור להמציא יעד עבורם.

נכון להיום מוגדרת רק שנת **2026**, עבור 4 נכסים: Black Forest (`GE-BF`),
Tabiano 1 (`IT-TAB1`), Chemnitz 1 (`GE-CH1`) ו-Tavernola (`IT-TAV`). כל
יעד כולל `revenue`, `expenses`, `profit` ו-`margin` (שבר, למשל `0.23` =
23%) — ונשמרים עקביים מתמטית (`profit = revenue - expenses`,
`margin = profit / revenue`) אלא אם צוין אחרת במפורש.

**לוגיקת החיפוש/צבירה/השוואה** (`src/lib/targets.ts`) קוראת אך ורק
מתצורת היעדים — ואינה נוגעת בנתוני ה-Excel או בחישובי ה"בפועל" (אלה
ממשיכים לבוא אך ורק מ-`calcRevenue`/`calcExpenses`/`calcProfit`/
`calcProfitMargin`, אותה שכבה שמזינה גם את הדשבורד הראשי ו-P&L):

- `targetedPropertyIds(year)` — רק הנכסים שיש להם יעד מוגדר לשנה הזו.
- `getTargetForSelection(year, propertyId, monthCount)` — יעד לנכס בודד,
  או **"כל הנכסים"** (`propertyId === "all"`) — שמייצג **רק את הנכסים
  שיש להם יעד מוגדר** לאותה שנה, לא את כל הנכסים במערכת. הבחירה
  "בפועל" מול היעד חייבת לייצג את **אותה אוכלוסיית נכסים** בדיוק
  (נאכף ב-`MonthlyTargets.tsx` דרך `getActual`, שמצטבר על אותה רשימת
  `targetedPropertyIds`).
- יעד משולב ("כל הנכסים") הוא **סכימה**, לא ממוצע: `getCombinedTarget`
  מסכם revenue/expenses/profit של כל נכס עם יעד, ושולי הרווח המשולבים
  תמיד `רווח משולב / הכנסה משולבת` — **לעולם לא ממוצע אחוזי השוליים
  של כל נכס בנפרד**.
- `compareToTarget`/`isTargetMet` — השוואת בפועל-מול-יעד, בטוחה מחלוקה
  באפס, ולפי קוטביות המדד (`KpiPolarity` מ-`lib/periods.ts`): הכנסה/רווח/
  שולי-רווח — עמידה = בפועל ≥ יעד; הוצאות — עמידה = בפועל ≤ יעד.

## 9. איך הקובץ נקרא ונשמר

כל הלוגיקה של קריאת הקובץ נמצאת ב-📁 **`src/data/loadExcel.ts`**
(פענוח בעזרת SheetJS) ו-📁 **`src/data/normalize.ts`** (מיפוי עמודות/
שמות גיליונות, כולל שגיאות כתיב, למבנה הפנימי הנקי שב-`types.ts`):

- `loadFromArrayBuffer(buffer)` — מפרק קובץ xlsx אמיתי, כולל **פיצול
  שתי הטבלאות בגיליון Properties** (A–C ו-E–H, עם זיהוי אוטומטי של שורת
  הכותרות גם כשיש מעליה כותרת-על ממוזגת), וזיהוי גמיש של שמות הגיליונות
  (גם עם שגיאות הכתיב, למשל "Maintence").
- `src/data/DataContext.tsx` — מקבל את הקובץ מההעלאה (`loadFromFile`),
  מפרק אותו, מעדכן את כל המסכים, ושומר עותק מלא ב-`localStorage`
  (מפתח `properties_dashboard_dataset_v1`) כדי שהנתונים יישארו אחרי
  רענון. בטעינה ראשונית: אם יש קובץ שמור — נטען אוטומטית (כולל תאימות
  לאחור לקבצים שנשמרו לפני הוספת `oneTimeExpenses`); אחרת מוצגים נתוני
  דמו.

אין שרת ואין חיבור רשת — הכול קורה בדפדפן עצמו. זה גם אומר שהקובץ שלך
**לא עוזב את המחשב** ולא נשלח לאף שרת חיצוני.

## 10. רעיונות לשדרוג עתידי (לא חובה ל-MVP)

1. **העלאה לשרת/ענן** — אם בעתיד תרצה שכמה מנהלים יראו את אותם נתונים בלי
   שכל אחד יעלה קובץ, אפשר להוסיף שרת קטן שמאחסן את הקובץ האחרון.
2. **חיבור אוטומטי ל-OneDrive / Graph** — אם תחזור למודל "משיכה אוטומטית",
   הקוד בנוי כך שקל להוסיף מקור נתונים נוסף לצד ההעלאה.
3. **מסד נתונים והיסטוריה** — שמירת כל קובץ שהועלה כדי להשוות מגמות לאורך זמן.
4. **התחברות והרשאות** — כניסת משתמשים והרשאות צפייה/עריכה.
